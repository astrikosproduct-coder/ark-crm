# spec/

`fields.json`, `picklists.json`, `stages.json`, `criteria.json`, `gates.json`, `thresholds.json`
and `seed/*.json` are **generated by `build_spec.py`** from
`ARK_CRM_Field_Register_Workbook_v4.xlsx`. `build_spec.py` lives outside this repo and will
overwrite these files wholesale. **Never hand-edit them.**

### Three exceptions, all in `seed/`, all temporary

`fields.json` and the rest of the register output remain untouched. Three edits have been
made to the **seed** files because no sidecar mechanism can express them, and **every one
will be lost on the next regenerate.** Each is listed on the Spec Health page under
*Questions raised while building a screen*, tagged `PROTOTYPE SEED EDIT`, so the same
correction can be made in the workbook's seed sheet:

1. `seed/accounts.json` — e& Enterprise (ACC-002) gained `End Client` alongside
   `Partner / SI`, so the journey's own partner demonstrates the dual-type model.
2. `seed/registrations.json` — both rows now use expiry = start **+ 89**, and REG-00051 was
   moved to 24 Oct 2025 → 21 Jan 2026. See "Rebasing the seed to demo day".
3. `seed/_anchor.json` — a new file, not from the workbook at all. See the same section.

## extensions.json — the sidecar

`extensions.json` is the one file here that is *not* generated. It exists because the field
register carries three things the form engine needs but cannot execute:

| Register column | Problem | Sidecar key |
|---|---|---|
| `computed_formula` | English prose against display labels — `"(ARR × Years) + Perpetual Licence Fee + …"` | `computed_expr` |
| `lookup_filter` | English prose — `"Account Type must include End Client"` | `lookup_filter_expr` |
| *(none)* | `childlist` fields declare no row shape at all — all 6 of them, in `leads` and `deals` | `child_spec`, every one `origin: "inferred"` |

…and two things it does not carry at all, held in top-level blocks rather than per field:

| Block | Problem |
|---|---|
| `list_views` | The register describes records, not screens. Nothing in it says which columns a list view shows, sorts by, or searches. |
| `seed_normalisation` | The seed sheets and the register sheets of the workbook disagree about api_names and picklist values for the same fields. |
| `partner_roster` | Nothing says which `accounts.account_type` values make an organisation a partner. |
| `partner_registration` | Playbook §6.2 states an exclusivity window and an acknowledgement SLA. The register carries neither as data. |
| `open_questions` | Gaps found by hand while building a screen, which no check over `fields.json` can detect. |
| `precision_limits` | Rules the playbook states more finely than the register's field types can carry. Not gaps — stated so no screen is read as claiming precision the data lacks. |

## Referring to a field: `module.api_name` is not unique

**Nine api_names are defined in two sections of one module** (three, for
`bids_pocs.status`). A sheet that describes several different records in one flat list of
rows produces these — `partners.partner` is written into both `DEAL REGISTRATION` and
`QUARTERLY SCORECARD`.

The prototype **contains** this rather than curing it. The register still carries the
duplicates and the Spec Health entry stays up until the register pass renames them.

| | |
|---|---|
| `field.qref` | `module.section.api_name`. Always unique. The identity of a field, and the right React key. |
| `field.ref` | `module.api_name`. A convenience **alias**, and only resolvable where the name is unique in its module. |

- The field index is keyed on `qref`. The `ref` index contains only unqualified-unique names,
  so `fieldOf('partners', 'partner')` returns `undefined` rather than whichever definition
  the register wrote last.
- Any sidecar key — a `fields` entry or a `list_views` column — may use either form. A
  **plain key naming a duplicated api_name stops the app at startup** with both candidate
  sections named. This is the one spec error that does not degrade gracefully: it would
  resolve to a real field, just not the one that was meant, and the screen would look
  entirely correct.
- An **expression** that mentions a duplicated api_name refuses to compile, for the same
  reason in reverse: an expression evaluates against a record, a record keys on `api_name`
  alone, and there is no value the identifier could honestly resolve to.
- `fieldsNamed(module, api_name)` returns every definition, for callers that only need to
  know whether the register carries the name at all.

## Rebasing the seed to demo day

Every date in the workbook is fixed, so a prototype opened months later shows a
registration that expired last quarter. Rather than editing the dates — which the next
regenerate would overwrite — `spec/seed/_anchor.json` names the day the seed sheet was
written against, and the loader shifts the **whole seed** by `today − anchor_date`. Every
interval the workbook chose is preserved exactly; only the origin moves.

```jsonc
{ "anchor_date": "2026-01-13" }
```

**Files here whose name begins with an underscore are configuration, not data.** `_anchor.json`
never becomes a collection.

- Shifted: `yyyy-MM-dd`, `yyyy-MM-ddTHH:mm…` (the time and zone are carried through as
  written, so nothing crosses a DST boundary by accident) and bare `yyyy-MM`, which is how
  `leads.expected_close_month` is stored. Every other string is left alone.
- Applied **on seeding only** — first run, and again on *Reset demo data*. Rebasing on
  ordinary load would move every record a day forward each day, and a lead created
  yesterday would never age.
- One delta is computed for the whole seeding, so two collections cannot disagree about
  what "today" was across a run that starts before midnight and ends after it.
- The result is stamped into `__seed` (anchor, date seeded, delta) and shown on the Settings
  page, so an operator can see whether the data in front of them is anchored to today.

### Why 13 January 2026

It is the day the journey document opens on. REG-00042 is acknowledged on 13 Jan and its
exclusivity runs to 12 Apr, so **on demo day that registration reads exactly 89 days left** —
the number the journey quotes. REG-00051 was moved to 24 Oct 2025 → 21 Jan 2026 so that it
lands eight days out and reads *Expiring*, giving one live registration of each kind on
opening the screen. As written, the two rows were 141 days apart, and no single anchor can
put both inside one 89-day window.

## The exclusivity window is 89 days, not 90

The window **includes the start day**: acknowledged 13 Jan, expires 12 Apr. The journey
document is authoritative, and both seed rows agree with it.

The register's own prose still reads *"Start date plus 90 days"* on
`partners.exclusivity_expiry_date` and is wrong by one day. It is shown unaltered in that
field's tooltip, with the sidecar's `note` underneath saying so — a reviewer needs to see
both, not be quietly handed the corrected one. The ambiguity is the real defect and it will
recur wherever else the register counts a window, so the fix is to restate it as *"plus 89
days"* or *"90 days inclusive of the start date"*.

## The acknowledgement SLA is stated in days

§6.2 gives acknowledgement a **48-hour** SLA. `partners.submitted_date` and
`acknowledged_date` are both typed `date`, so elapsed time is only knowable to the whole
day. The type is **not** being changed and no time component is faked. Instead the rule is
applied — and always stated — as **2 days**: *"acknowledged in 1 day, inside the 2-day
rule"*. Nothing in the app displays or computes hours.

This is a `precision_limit`, not an `open_question`: it is not a gap somebody is expected to
fill. Reopen it only if 48 hours is meant literally rather than as "within two working
days", which would mean typing both fields `datetime`.

The loader (`src/lib/spec/index.ts`) merges `extensions.json` over `fields.json` at import
time, keyed by `"<module>.<api_name>"`. A regenerate of `fields.json` leaves this file
untouched, which is the whole point of the arrangement.

`computed_formula` is **never parsed**. It stays exactly as the register wrote it and is used
only as the ⓘ tooltip text next to a computed field, so a reviewer sees the business
statement, not the machine expression.

### Keys

- **`computed_expr`** — an executable expression. 26 of the 30 fields that carry a prose
  formula have one.
- **`lookup_filter_expr`** — a predicate evaluated against records in the target collection.
  6 of 7.
- **`child_spec`** — the row shape of a `childlist`. 6 of 6, and **all six are
  `origin: "inferred"`** — see below.
- **`unexpressed`** — a written reason why a field that *should* have had one of the above
  does not. These surface on the Spec Health page. A field with `unexpressed` renders
  read-only and blank rather than showing an invented value.
- **`note`** — records a judgement call made while translating, so the register correction
  pass can check it.

### `child_spec` — childlist row shapes

```jsonc
"leads.demo_attendees": {
  "child_spec": {
    "origin": "inferred",                  // or "stated"
    "basis": "Derived from the field's own description and use_case…",
    "add_label": "Add attendee",
    "row_noun": "attendee",
    "columns": [
      { "api_name": "attendee", "label": "Attendee", "type": "lookup",
        "lookup_target": "contact", "required": true, "width": 220 },
      "leads.milestone_—_planned_date"     // …or a ref to a field the register carries
    ]
  }
}
```

A column is either an **inline object** — `api_name`, `label`, `type`, `required`, `width`,
plus `picklist` / `lookup_target` / `lookup_filter_expr` / `computed_expr` as its type needs
— or a **`"<module>.<api_name>"` ref**. A ref means *this column IS that field* and inherits
its type, picklist, lookup, formula and **requirement**: that is how the four
`milestone_—_*` and seven `guarantee_—_*` fields become row columns without being restated,
and why Planned Date is demanded on a milestone row while the other three dates, `Conditional`
in the register, are not. Both forms resolve to one shape at load
(`src/lib/spec/childSpec.ts`), and a cell renders through the same `FieldControl` every other
field on a screen uses — there is deliberately no second set of table-only controls.

**Rows are part of the record's value.** The form provider merges them into `values` under
the childlist's own `api_name` and `toPayload` persists them there, so a childlist is just
another value to validation, the readiness panel, draft persistence and view mode's
hide-what-is-empty rule.

**A `computed_expr` on a column is evaluated once per row.** Its identifiers resolve to a
sibling column **first** and to a field of the parent record **second**, so
`guarantee_—_value / contract_value` reads the row's guarantee value and the deal's contract
value in one expression. A name in neither namespace throws rather than quietly evaluating to
null. A `lookup_filter_expr` on a column keeps its usual semantics — it runs against the
target collection only and **cannot see the parent record**, so "contacts at this lead's End
Client" is not expressible; that limitation is in `open_questions`.

#### `origin` — and why none of the six is `"stated"`

`origin: "stated"` means the register actually defines the row shape. `origin: "inferred"`
means somebody derived it, and `basis` must say from what.

The register defines a row shape for **none** of the six childlists in `leads` and `deals`.
It plainly knows how — the `bids_pocs` sheet carries `BID CHECKLIST ITEM (child)`,
`TBE QUERY (child)`, `POC SUCCESS CRITERION (child)` and `POC USE CASE (children)` as
explicit child sections with their own typed columns. Nothing equivalent was written for
`demo_attendees`, `feature_gaps_logged`, `payment_milestones`, `bid_commitments_register`,
`expansion_use_cases` or `linked_expansion_leads`.

So every `child_spec` here is a proposal. Each one:

- renders a working editable table, so the columns can be argued with in front of real data;
- wears a **"proposed shape"** chip beside its field label, whose tooltip is the `basis`;
- carries a comment pin on that same label, like any other field, so "wrong columns" lands
  on the thing being looked at;
- **stays on the Spec Health page.** Fixing the render does not close the gap. Only a
  `child_spec` marked `origin: "stated"` drops off that list, and nothing should be flipped
  to `"stated"` because the table works.

### `list_views`

```jsonc
"accounts": {
  "columns": ["accounts.account_name", "accounts.account_type", …],  // refs into fields.json
  "default_sort": "account_name",                                    // bare api_name
  "search": ["account_name", "country", "segment"]                   // bare api_names
}
```

Columns are `"<module>.<api_name>"` refs, so a list can never name a column the register does
not carry — a ref that no longer resolves is dropped from the screen and reported on Spec
Health. A module with no entry gets a list screen that says so rather than one that invents a
column set. `search` is passed to the list endpoint as `_search`, so what the text filter
looks at is spec, not component code.

### `partner_roster` and `partner_registration`

A partner is **not** a separate kind of organisation. A partner is an account whose
`account_type` includes a partner type, so the Partners list is a view over
`/api/accounts` and e& Enterprise is one record seen from two screens. `partner_roster`
names which types qualify, because the register never says — `leads.customer_partner_si`
filters on `PARTNER_SI` alone, yet the seed gives Schneider Electric
(`OEM_TECHNOLOGY_PARTNER`) both a `partner_tier` and a `partner_type`.

`partner_registration` holds the three numbers Playbook §6.2 states and the register does
not carry: `exclusivity_days` (**89** — see below), `acknowledgement_sla_days` (**2** — see
below) and `expiring_within_days` (15, chosen for the prototype). It also holds two **field
sets** — named subsets of one register section, resolved by `fieldsInSet()`:

```jsonc
"capture_fields": {
  "module": "partners",
  "section": "DEAL REGISTRATION",
  "fields": ["partner", "end_client", …]   // bare api_names, in render order
}
```

`DEAL REGISTRATION` describes two screens at once: the seven fields a partner submits and
the five ARK stamps on acknowledgement. A create form that offered all fifteen would invite
somebody to type an exclusivity date by hand, so the subset is spec rather than a literal in
a component. A name the register no longer carries is dropped and reported on Spec Health,
exactly as an unresolvable `list_views` column is.

**The Partners sheet defines no partner-organisation fields at all.** Its three sections are
`DEAL REGISTRATION`, `CONFLICT ADJUDICATION` and `QUARTERLY SCORECARD` — all child records
of a partner. The partner-only attributes are a section of the *Accounts* sheet, so there is
deliberately no `partners` collection and no `spec/seed/partners.json`: one would store the
same seven values in two places. This is the first row of `open_questions`.

### `open_questions`

```jsonc
{ "ref": "partners.submitted_date", "detail": "Typed `date`, but §6.2 puts a 48-HOUR clock on it…" }
```

`ref` is a `module.api_name`, or a bare module when the question is about the sheet as a
whole. These render on the Spec Health page beside the generated groups. The distinction
matters: every other group there is *derived* from `fields.json` and disappears when the
register is corrected, whereas these were hit by a person making the register drive a real
screen and have to be removed by hand once answered.

### `seed_normalisation`

```jsonc
"accounts": {
  "module": "accounts",                                   // whose api_names to use
  "rename": { "name": "account_name", "account_types": "account_type" }
}
```

The workbook's seed sheets were filled in separately from its register sheets and the two do
not agree:

| Register says | Seed writes |
|---|---|
| `accounts.account_name` | `name` |
| `accounts.account_type` | `account_types` |
| `contacts.friend_foe_assessment` | `friend_foe` |
| `contacts.contact_role = "DECM_DECISION_MAKER"` | `"DECM"` |
| `accounts.account_type = "END_CLIENT"` | `"End Client"` |

Both files are generated, so neither can be corrected by hand. The mapping therefore lives
here and `src/lib/spec/seed.ts` applies it once as the store loads: keys are renamed, then
every picklist- and multiselect-backed value is coerced to its picklist **key** — matching on
key, label, slug, or the leading code of the key (`DECM` → `DECM_DECISION_MAKER`). A value
that matches nothing is left exactly as written and reported, never blanked.

**Every line of this block is a defect in the workbook.** All of them appear on the Spec
Health page under *Seed data that does not match the register*, and the block should shrink
to nothing once the seed sheets are corrected.

One consequence worth knowing: because `account_type` now holds keys, the two account lookup
filters are written against keys — `account_type includes 'PARTNER_SI'`. Slug comparison
cannot reconcile `PARTNER_SI` with the label `Partner / SI`, since the slash survives folding.

### Expression language

Recursive descent, no `eval`, no `Function`. See `src/lib/spec/parser.ts`.

```
literals     123   1.5   'text'   "text"   true   false   null
identifiers  bare api_name of a field in the same module
             leading digits are fine:  3rd_party_one_time, 3_year_tco
             em-dashes are fine:       guarantee_—_value
             backtick-quote anything awkward: `conversion_rate_to_stage_4+`
operators    ? :   ||   &&   ==  !=   <  <=  >  >=   includes   +  -  *  /   !  -
functions    sum(child, field, filter?)   concat(…)   coalesce(…)   round(n, dp?)
             min(…)  max(…)  abs(n)  if(test, a, b)
             add_days(date, n)   days_between(a, b)   business_days(a, b)
```

Identifiers are resolved against the module's `api_name` set **at load**, so a typo in this
file throws on startup naming the expression and the bad identifier, rather than silently
evaluating to `undefined`.

**Empty-value semantics follow a spreadsheet, not JavaScript.** An arithmetic operator with
all-empty operands yields blank, not `0`; with some operands present, empty counts as `0`.
Division by zero yields blank, never `NaN` or `Infinity`. So Total Value (TCV) reads blank on
an untouched lead instead of `$0`.

A numeric *literal* counts as a present operand, exactly as it would in Excel — `arr * 3` on
an empty record gives `0`, while `arr * years` gives blank. This is what makes
`gross_line * (1 - discount_pct_applied)` correct when no discount has been entered: the
`1` keeps the bracket live, so a blank discount reads as no discount rather than as a
100% one.

### String comparison has two different rules — deliberately

- In `computed_expr` and `visibility_condition`, a literal compared against a **picklist** or
  **multiselect** field is normalised through `picklists.json` and matches on either the key
  or the label. `deal_source == 'Partner-sourced'` therefore holds whether the stored value
  is `PARTNER_SOURCED` or `'Partner-sourced'`.
- In `lookup_filter_expr` the operands are rows in a target collection, not spec fields, so
  no picklist is available. Comparison there is **slug-normalised** — case-folded, with
  `-`, `_` and space treated as equivalent. This is forced by the seed data being
  inconsistent: `users.roles` stores keys (`"BD_OWNER"`) while the register's prose names
  labels. Collections listed in `seed_normalisation` are already coerced to keys by the time
  a filter runs, so filters against those should name keys and not rely on slug folding.

## To fold back into build_spec.py

The three keys above should eventually become three columns in the workbook, at which point
`extensions.json` shrinks to nothing and is deleted:

1. `computed_expr` next to `computed_formula`
2. `lookup_filter_expr` next to `lookup_filter`
3. `child_spec` for `childlist` fields
4. a list-view sheet, replacing `list_views`
5. `seed_normalisation` should not be folded back — it should be **deleted**, by correcting
   the seed sheets to use the register's own api_names and picklist keys.

Two register problems are worth fixing at the same time, because they make api_names awkward
to reference in any expression language:

- **Nine api_names are defined twice within one module** — see "Referring to a field"
  above. Contained, not cured; the register still has to rename them.
- Some api_names begin with a digit — `3rd_party_one_time`, `3_year_tco`, `5_year_tco`.
- Some contain an em-dash — `guarantee_—_value`, `subtotal_—_modules`,
  `rate_per_hour_—_onsite`, `milestone_—_planned_date`.
- One contains a `+` — `conversion_rate_to_stage_4+`.

The parser handles all three, but they are hostile to every other tool that will touch this
data later.
